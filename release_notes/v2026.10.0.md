## Highlights

2026.10.0 is the October stable. The headline is cloud suppression finally doing something sensible for the cover while it holds: a tilt-only venetian can now take a slat angle during the cloud, and the cover can open fully once the cloud has held past a delay you choose (#175). Alongside it, tilt covers get a floor on the angle the sun leaves the slats at, for facades where the reflection off the slats is its own glare problem (#1282), and an opt-in that snaps a barely-open sun-tracking position the rest of the way closed (#1379). Diagnostics get clearer: the sun-tracking gate now names the sensor or template holding it shut (#1359), sensor and binary sensor names follow the Home Assistant language, thanks to a contribution from @jfhautenauven (#1352), and Last Cover Action shows the position it sent (#1197). On the fix side, Adaptive Cover Pro now owns its own device linked to the physical cover instead of colliding with Home Assistant 2026.8's device model (#1369), turning automatic control off no longer opens and then immediately re-closes an inverse-state cover (#1376), and two false-override and re-send loops on slow or finicky hardware are closed (#1350, #1358). Several state strings and the device layout change for existing installs and are spelled out under Upgrade notes.

## Features

**A cloudy slat angle and a cloud escalation delay (#175):** Cloud suppression named no tilt at all, so on a tilt-only venetian the carriage was pinned closed and the slats froze wherever the last sun-tracking cycle left them. The reporter's diagnostics showed cloud suppression winning with position 100, the venetian tilt-only rewrite turning that into 0, and no tilt command anywhere in the trace. I added a clearable `cloudy_tilt` ("Cloudy slat angle (optional)") so the handler commands a slat angle while suppression holds. Left empty, the slats stay where they are, which is the behaviour before this option existed. It is offered only on cover types with an independent slat axis. A cloudy slat angle alone still leaves the blind down for as long as the cloud lasts, so I also added `cloud_escalation_delay` ("Open fully after (optional)"): once suppression has held continuously for that long, the cover opens fully instead of staying at its cloudy position. The escalated position is the unshaded one for the cover type, not a hardcoded 100, so an awning retracts rather than extending after a long overcast spell. On a tilt-only venetian the carriage opens too. The delay is not the smoothing hold time: the hold time decides how quickly suppression engages, this decides how long it may stay engaged, and a brief sunny spell resets the clock. The deadline is derived on every read from the moment suppression engaged, so changing the delay mid-hold takes effect at once, and a new Cloud Escalation End Time sensor persists it across a restart so a daily-restarting install does not hand itself a fresh full hold every time. The escalation position is emitted only from inside the handler's normal evaluation, so the field-of-view guard from #417 still applies. Both options are empty by default, so existing installs are unchanged and no migration is needed. The configuration summary's "configured but cloud suppression is off" warning is now one guard covering every cloud setting.

**A reflected-sun floor for tilt covers (#1282):** Above the profile angle beta = arctan(slat distance / depth), the cut-off solve returns a past-horizontal slat with its outer edge up, and its upper face mirrors the beam into the room. Direct sun is still blocked, but on a large south facade with floor-to-ceiling glazing the reflection is a glare source of its own. The new `tilt_min_reflected_elevation` ("Minimum Reflected Sun Angle", 0 to 90 degrees, 0 disabled) sets the lowest angle above horizontal the reflected beam may leave at. The slats are tilted back toward, or past, horizontal just far enough to reach it, and are never opened beyond the direct-sun cut-off. It runs after the safety margin, because the margin's past-90 branch would otherwise undo it. Minimum Slat Tilt is applied afterwards and can re-open the slats past this cap, so keep that floor low; the help text says so. Louvered roof covers do not get the option, since their slat geometry invalidates the mapping the constraint relies on. At 0 the output is unchanged, so there is no migration. I pinned that against output generated from the pre-change engine rather than the new one.

**Snap a barely-open sun-tracking position closed (#1379):** A sun-tracking demand of 2 or 3% only lets a sliver of light through and leaves the cover looking mistakenly ajar. Two opt-in options, "Snap closed below threshold" (`snap_closed_below`, off by default) and "Snap closed threshold" (`snap_closed_threshold`, 1 to 50 percent, default 10), collapse any position inside that band to the closed endpoint. It applies to the position axis and to sun-tracking positions only; climate, weather and sunset keep their own intent, and tilt axes are left alone. An active minimum position always wins over the snap. On an awning the snap target is 100, not 0. The forecast strip that feeds the diagnostic sensor and the companion card's elevation chart now plots the snapped value, so they agree with what the cover is commanded to. The configuration summary gains a line for the option and warns when an always-on floor or ceiling already covers the whole snap band, which would make the setting inert, and when a group mixing a position-capable cover with an open/close-only one keeps the sun-tracking floor active for the whole group, so a snapped demand settles at 1% on the blind that could have reached 0%. Both options default off, so existing installs are unchanged.

**The sun-tracking gate names what is holding it shut (#1359):** A closed sun-tracking gate parks the cover at its default position for as long as the gate stays closed, and nothing said which entity was responsible. Diagnosing one took a diagnostics download and a read of the code. The skip reason now names the cause as one of three whole clauses: the blocking sensor or sensors, the gate template, or both. In AND mode a false template closes the gate on its own with every sensor on, so a sensor is only named when the sensor side itself resolved false; an unavailable sensor abstains rather than blocks. The decision trace in diagnostics now exports `reason_code` and `reason_params`, and the offline triage rule for this case keys on that stable code instead of the English prose, so it still fires on a German or French install. It fires only when the default handler actually won, so a manual override or weather rule driving the cover is not misreported as a parked cover.

**Entity names and diagnostic states follow the Home Assistant language (#1352):** Thanks to [@jfhautenauven](https://github.com/jfhautenauven), who contributed this (original report #513). Sensors, binary sensors and the Reset Manual Override button now resolve their names through `translation_key` instead of hardcoded English, so Settings > Devices follows the HA language, and English, German and French state translations cover Control Status, Occupancy Status, Climate Status and every Last Skipped Action reason. New covers on German and French installs get entity IDs built from the localized names; existing entities keep theirs, and a frozen English-name snapshot keeps English entity IDs from drifting. Last Skipped Action's idle state changes, see Upgrade notes. The Building Profile, Command Queue and sync-confirm localization, the localized device models and the Last Cover Action state change were taken out of this PR before merge; the parent tracker is #1353.

**Last Cover Action shows the sent position (#1197):** The state carried the service, the entity and the timestamp, with the position only as an attribute. HA's history and logbook render an entity's current attributes beside historical state rows, so scrolling back through past rows showed today's position on every one of them. The state now reads service, entity, position and time, and falls back to "unknown" for a stored action with no position, which happens on a cover with no set-position support. The attributes are unchanged.

**The Outside Temperature switch is visible by default (#1125):** The per-cover Outside Temperature switch gates whether the outdoor sensor drives the winter/summer decision, but it shipped registry-hidden as well as off, so configuring an Outdoor Temperature Entity looked like it mattered and silently did not. It now appears on the device page. It stays off, so the season still runs on the indoor sensor until you turn it on. This applies to new registrations only: Home Assistant applies the default when an entity is first registered, so an existing install keeps the switch registry-disabled and needs a manual enable.

## Fixed

**ACP now has its own device, linked to the physical cover (#1369):** ACP used to borrow the physical cover's device identifiers so its entities merged onto that device card. Home Assistant's version 3 device registry, shipped in 2026.8, scopes identifier lookup by config entry, so the borrow stopped merging and created a second, ACP-owned duplicate. Anyone on 2026.8 or later has had two device cards since August. ACP now owns a service device and links it to the physical one with `via_device_id`, mirroring the physical device's area and re-asserting it when the area moves. That is the only cross-entry link Home Assistant sanctions. An existing duplicate is adopted in place by rewriting its identifiers, so its device id and every entity binding survive. Adoption only happens when the device holds at least one of our entities and the service device does not exist yet, so it can never reach a co-owned physical device. A leftover that holds none of our entities is offered as a Repair instead of being removed silently, and one holding only entities we do not own is logged and left alone with no Repair. The stored device id is no longer trusted for lookups, since the version 3 migration gives every split a fresh id; the physical device is resolved through the cover entities' registry entries. Reads of the deprecated device properties are routed through one version-gated probe, so setup is quiet on Home Assistant's development builds and on the 2026.3.0 floor alike.

**Turning automatic control off no longer opens and then closes an inverse-state cover (#1376):** The return-to-default dispatch run by turning automatic control off handed the configured default to the cover in the logical frame, while every other producer re-frames first. On an `inverse_state` install it sent the mirror of the intended position: an awning with default 0 got `close_cover` (extend), and the refresh on the next line immediately sent the correct `open_cover` (retract), which is the "opens and then closes" the reporter saw. The end-of-window fan-out and this seam now share one broadcast method that clamps, re-frames and orders on the wire number. A cover already at its default hits the existing same-position gate and sends nothing. The diagnostics configuration block also gains `return_to_default_toggle` and `automatic_control`, and both dispatch sites thread trigger, force and safety through, so a diagnostics dump can attribute a command to the seam that sent it. The end-of-window seam now records its event before the dispatches it causes.

**A pinned min/max limit no longer re-fires every cycle on hardware that reads back 1% off (#1350):** The configured `min_position` and `max_position` have had a permanent exemption from the movement-delta gate since #474, so the cover is guaranteed to reach a pinned limit at least once. That guarantee is one-shot but nothing ever closed it, so on hardware that reads back a position 1% off the commanded value the bypass re-fired every cycle. On a coupled venetian each 1-point carriage command collapses the slats by about 61 points, which triggers a drift retry, and the loop repeated for the whole solar window. The exemption is now one-shot per approach, mirroring the anti-relay latch the 0 and 100 endpoints already use. The first approach still bypasses the delta gate in full; repeats fall through to the normal threshold and report `delta_too_small`. The latch arms only after a successful dispatch, flipping between floor and ceiling re-arms each in turn, and the literal 0 and 100 values stay out of it, since the endpoint path already governs them.

**A fast cover's arrival inside command grace now settles the wait, so a reversal registers as a manual override (#1358):** While an entity was in the 5-second command grace, classification returned before the one arrival-driven check that clears the wait for target. A cover that finishes travelling inside the grace window, the reporter's Tuya shutter runs 0 to 100 in 0.87 seconds, therefore had its arrival discarded and could only be released by the 45-second transit timeout. In that stale window the first sample of a user's reversal looks identical to the firmware echo the optimistic-target guard was built for in #518, so the guard restarted grace and swallowed the reversal, and Position Verification re-sent on a timer, so the manual override never engaged. A verified arrival, one where the previous position differs from the position at send, which an echo cannot produce, now settles the wait from inside grace and the reversal reaches the override logic on its first sample. Gated manual-override rejections also report the position the cover published instead of a hardcoded none, which had made this class of report read as though the cover published nothing.

**Group rosters follow a device that changes area (#1339):** Home Assistant deprecated using the device and entity registries as mappings, and the pattern stops working in 2027.9.0. All four full-registry scans are replaced with the registries' indexed accessors, and a test now fails on any new mapping-shaped scan under `custom_components/`. While there I found that an area-scoped cover group never heard about a device moving between areas, because no entity-registry event fires for it, so membership inherited from a device could go stale indefinitely. The group coordinator now subscribes to device-registry updates and re-resolves its roster, comparing membership rather than order so a pure reshuffle does not reload anything.

**Sunrise-gated window and return-to-default switch on tilt covers (#1340, #1349):** these already shipped in v2026.9.1; nothing new ships for them here.

## Upgrade notes

**Last Skipped Action's idle state string changes (#1352):** The idle state was the English text "No action skipped" and is now the state key `no_action_skipped`, which Home Assistant renders as "No Action Skipped" in English and translates in German and French. Any automation, template or dashboard condition that compares the state to the old string needs updating.

**Last Cover Action's state now includes the position (#1197):** It reads service, entity, position and time instead of service, entity and time. Anything that parses the state text needs updating; the attributes are unchanged.

**Device registry change on Home Assistant 2026.8 and later (#1369):** Cover entities move onto ACP's own service device, which is linked to the physical device and mirrors its area. An existing duplicate device is adopted in place, so its device id is preserved for dashboards and automations that reference it. You may see a Repair for a leftover duplicate that holds none of ACP's entities; check it before dismissing it.

**Inverse-state installs (#1376):** Turning automatic control off now sends the default position the right way round. If you had worked around the open-then-close flicker, you can drop the workaround.

**No config-entry migration.** Every new option is empty or off by default and reads as the pre-existing behaviour when absent. The Outside Temperature switch's new visibility reaches new registrations only.

## Internal

- #1274: the manual-override state model collapses to one frozen `OverrideState` store per entity, where presence in the store is liveness, replacing four dicts kept in agreement by convention. Dead detector surface is pruned and the detector's state-change inputs travel as one dataclass. Behaviour-neutral; diagnostics keep every key and value.
- #1061: the window-end "is it configured" predicate is read from one source instead of three hand-rolled definitions that disagreed about the empty string. One edge case changes: `TimeWindowManager.after_start_time` with a blank start and an empty-string end bound now reads as unbounded instead of sunrise-anchored. Such an install had no resolvable end, so the sunrise anchoring from #1256 never applied to it. The `BLANK_TIME` value every cleared time selector writes is unaffected.
- #1373: the stable CI leg's test harness was pinned to a version resolving to Home Assistant 2026.6.3, three minor releases behind what users run. It is bumped to a harness version resolving to Home Assistant 2026.9.2, brittle white-box registry mocks are replaced with real registry fixtures, and the registry index guard now scans `tests/` as well.
- #1368: the golden-value check for the reflected-sun floor compared trig-derived floats with exact equality and failed on every CI run because macOS and Linux disagree by 1-2 ULP; both halves of each row now use one relative tolerance.
- #1337: the pre-commit ruff hook is aligned with the version CI enforces.

15651 tests passing, 4 skipped, 1 xfailed.

## Compatibility

Home Assistant 2026.3.0+ and Python 3.11+. `ConfigFlowHandler.VERSION` stays 3 and `MINOR_VERSION` is unchanged from v2026.9.1, so nothing is rewritten in an existing config entry and a rollback finds its configuration exactly as it left it. New options (the cloudy slat angle, the cloud escalation delay, the reflected-sun floor, and snap closed) all read as their pre-existing behaviour when absent, so upgrading changes nothing on its own. The device-registry change applies on Home Assistant 2026.8 and later. The companion Lovelace card ([jrhubott/adaptive-cover-pro-card](https://github.com/jrhubott/adaptive-cover-pro-card)) is a separate repo with its own release cycle and needs no update for this release.
